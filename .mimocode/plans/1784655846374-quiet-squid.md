# Context Window Analysis for Multi-Step Commands

## Current Context Window Budget

The Ollama model (qwen3:0.6b) uses **4096 tokens** total. Here's how it's consumed:

### Token Breakdown (Estimated)

| Component | Tokens | Notes |
|-----------|--------|-------|
| System prompt (base) | ~800 | JARVIS_SYSTEM_PROMPT_BASE in jarvis.py:252 |
| Memory context (8 sources) | ~300-600 | memory_injector.py — user profile, screen, mood, patterns |
| Personality genes | ~50 | tilde_frequency, conciseness modifiers |
| Tool definitions (20-40 tools) | ~1500-3000 | tool_tiering.py filters to relevant tools |
| **Total pre-response** | **~2650-4450** | |
| **Remaining for conversation** | **~50-1450** | Very tight! |

### For "open opera and search AI news"

1. **System + tools**: ~3000 tokens consumed
2. **User message**: ~10 tokens
3. **Available for LLM response**: ~1086 tokens
4. **LLM needs to generate**: 2 tool calls (open_app + web_search) = ~80 tokens
5. **Tool results fed back**: ~100 tokens
6. **Second LLM call**: summary response = ~50 tokens

**Total conversation tokens**: ~1320 — fits in 4096 but barely.

### For "open notepad and type a long paragraph"

1. Same initial consumption: ~3000 tokens
2. **type_text with long content**: The content itself goes in tool args, NOT in the LLM context
3. **Tool results**: ~200 tokens per round
4. **Agentic loop (up to 5 rounds)**: Each round adds ~300 tokens

**Risk**: With 5 rounds of agentic loop, total could reach ~4500 tokens — exceeds 4096!

## The Problem

The context window is **too small** for reliable multi-step commands:

1. **No token counting** — The system never checks if it's about to exceed the context window
2. **No truncation** — System prompt + tools + history can overflow silently
3. **4096 is tight** for phi4-mini:3.8b which has native 128K context
4. **Tool definitions consume too much** — 20-40 tools = 1500-3000 tokens

## Recommended Fix

### Set num_ctx to 131072 (128K)

phi4-mini:3.8b supports 128K context natively. Set it to the max.

**Files to modify:**
1. `backend/llm/ollama_client.py:189` — Change default from 4096 to 131072
2. `backend/llm/providers.py:907` — Change hardcoded 4096 to 131072
3. `backend/llm/providers.py:1581` — Change hardcoded 4096 to 131072
4. `backend/llm/Modelfile` — Change `PARAMETER num_ctx 4096` to `PARAMETER num_ctx 131072`
5. `backend/llm/Modelfile.main` — Change `PARAMETER num_ctx 4096` to `PARAMETER num_ctx 131072`
6. `backend/llm/Modelfile.router` — Change `PARAMETER num_ctx 4096` to `PARAMETER num_ctx 131072`
7. `backend/intelligence/auto_tuner.py:102` — Update default to 131072, max to 131072

**Note:** The router model (qwen3:0.6b) also supports 32K natively, so 128K is fine for both models.

## Verification

After making changes:
1. Run `pytest tests/ -q` — all tests should pass
2. Restart Ollama to pick up new Modelfile settings: `ollama stop; ollama serve`
3. Recreate models with new context: `ollama create may-main -f backend/llm/Modelfile.main`
4. Test: "open opera and search AI news" — should work reliably
5. Test: "open notepad and type hello" — should work without context overflow
6. Test: "what time is it" — should still be fast (fast-path, no LLM)

## VRAM Impact

With 128K context, KV cache memory increases:
- qwen3:0.6b at 128K: ~0.5GB VRAM (was ~0.1GB at 4K)
- phi4-mini:3.8b at 128K: ~2.0GB VRAM (was ~0.2GB at 4K)
- Total: ~2.5GB VRAM for KV cache (within 6GB budget)

With flash attention enabled (`OLLAMA_FLASH_ATTENTION=1`), actual usage is ~30-50% lower.
